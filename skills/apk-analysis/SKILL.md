# Using asc-rs (APK analysis CLI)

Binary: `asc-rs` (Windows: `asc-rs.exe`) — a standalone prebuilt executable, no JVM/Python/Rust toolchain needed. If `asc-rs` is not on PATH, locate the shipped binary in the environment rather than building anything. Lazy, on-demand; no preprocessing. Run `asc-rs <cmd> --help` for flags.

The same engine ships as a GUI workbench: `asc-gui <apk>` (`--selfcheck <apk>` for a headless smoke). It adds a class tree, decompiled/Smali/bytecode/CFG views, call trees, R8 `mapping.txt` search and an extracted-resources browser on top of the CLI's query engine.

## Commands

```
asc-rs findrefs <apk> string <substr>            # callers of a string-pool match
asc-rs findrefs <apk> type   <substr>            # callers referencing a type descriptor
asc-rs findrefs <apk> method [name] [--class C [--fuzzy-class]]
asc-rs findrefs <apk> field  [name] [--class C [--fuzzy-class]]
asc-rs findrefs <apk> extends|impl <Lpkg/Cls; | pkg.Cls> [--transitive]   # classes defined in the APK that extend / implement it
asc-rs getclass <apk> <Lpkg/Cls; | pkg.Cls>      # decompile ONE class
asc-rs disasm <apk> <Lpkg/Cls; | pkg.Cls> [--method NAME] [--view smali|bytecode|cfg]   # Smali listing (default), raw bytecode table, or per-method basic blocks of ONE class
asc-rs calls <apk> <Lpkg/Cls; | pkg.Cls> --method NAME [--depth N] [--max-nodes N]   # outgoing call tree of one method (breadth-first, default depth 1)
asc-rs member <apk> <Lpkg/Cls; | pkg.Cls> --method NAME          # signature + access flags of every overload of one method
asc-rs mapping <mapping.txt> <needle>                            # R8/ProGuard mapping lookup, original <-> obfuscated names
asc-rs listclass <apk> [-o FILE]                 # all class descriptors, DEX order
asc-rs listmethod <apk> [--class C] [--name SUBSTR] [--limit N]   # methods DEFINED in the APK: `Lcls;->name(params)ret`
asc-rs manifest <apk> [-o FILE] [--match-uri URI]  # full manifest: package, split markers, application attrs + meta-data, permissions (maxSdk), uses-features, queries, components with deep-link data/aliases; --match-uri evaluates each filter's API-35 URI-relative reachability
asc-rs inspect <apk|dex> [-o FILE]               # entry inventory (incl. Hermes bundles), DEX coverage/checksums, packer signals, split-APK status, manifest-vs-DEX check
asc-rs native  <apk|dex> [-o FILE]               # lib/ + assets/*.so ELF inventory, DEX native methods, JNI export name match + static RegisterNatives table match; notes missing ABI splits
asc-rs cert    <apk> [-o FILE]                   # signing certs: JAR v1 + APK Signature Scheme v2/v3; every signer verified
asc-rs resources <apk> [--id 0x7f020000 | --strings PAT] [--limit N] [-o FILE]   # resources.arsc inventory / lookup / search
asc-rs strings <apk|dex> [--substring PAT] [--limit N] [-o FILE]   # every DEX string-pool entry (multidex + DEX-041), with source DEX + index
asc-rs strings <apk|dex> --class <Lpkg/Cls; | pkg.Cls> [--substring PAT]   # only the string constants that class's code loads, with site counts
asc-rs extract <apk> <entry> [-o FILE] [--verify-crc]   # pull one entry out (safe basename by default, optional CRC check)
asc-rs axml    <apk> <entry> [-o FILE]           # decode any compiled binary-XML entry (res/xml/*, manifest) to text/JSON
asc-rs hermes  <apk> [--pattern PAT] [--limit N] [-o FILE]   # structured string-table extraction from Hermes bundles (bytecode v59 and v74..=96; other versions reported unsupported)
asc-rs xapk    <file.xapk> [-o FILE]             # XAPK container inventory: member APKs (manifest, DEX class counts, native libs) analyzed per member, never merged
Input: an APK/ZIP **or a bare `.dex`** (DEX 035..041; e.g. a runtime-dumped DEX). A bare DEX is one virtual entry named after the file: `manifest`, `cert`, `resources` on it exit `2` ("requires an APK"); `extract`/`axml` on a missing entry exit `1`, on the dex-named entry `extract` exits `0` (raw bytes) and `axml` exits `2` (a DEX is not binary XML); an unparseable or CDEX/ODEX/VDEX file exits `2` with a clear error instead of empty output.
Shared flags (any position): `-o FILE`, `--threads N` (default 8), `--debug` (timings to stderr), `--format text|json` (all commands), `--paranoid` (decode Paranoid/LSParanoid strings; off by default), `--decode-xor` (decode const-array XOR strings; off by default), `--mapping mapping.txt` (translate an ORIGINAL class name given to `getclass`/`disasm`/`calls`/`member`/`findrefs method|field --class` into the obfuscated name; stderr `mapping: orig -> obf`; unknown names pass through unchanged with a stderr note; unreadable file exit `1`; `--fuzzy-class` is not translated). It also annotates `findrefs`/`listclass`/`calls`/`member` output: obfuscated names are printed unchanged and the originals are ADDED — text: trailing `    # Lobf;->m = Lorig/Cls;->name` per line, JSON: a top-level `"mapping": {obf: orig}` object (always present with `--mapping`, `{}` when nothing matched). Members shared by several originals print `a|b`. `getclass`/`disasm` output is never renamed).

## Choosing the command

| Goal | Use |
|---|---|
| Who uses URL / key / log text | `findrefs string` |
| Who calls API X (e.g. `getSystemService`) | `findrefs method X` |
| Who calls anything on class C | `findrefs method --class C` (no name) |
| Who touches a field | `findrefs field` |
| Who references a type (e.g. `Ljava/lang/StringBuilder;`) | `findrefs type` |
| Class name unknown | `listclass`, filter output, then `getclass` |
| Subclasses of X / implementors of interface X (e.g. all `Activity`s, `Binder` stubs) | `findrefs extends X` / `findrefs impl X` (`--transitive` for the whole subtree) |
| Which classes define method `onReceive` / every method of class C with its signature | `listmethod --name onReceive` / `listmethod --class C` |
| Package, permissions, exported components (declared vs inferred vs **install-invalid**), receivers, deep links (pooled `scheme`/`host`/`path` match set + inert-dimension flags + API 35 `<uri-relative-filter-group>` warning — see Pitfalls), meta-data, split markers | `manifest` |
| Is this sample packed / is there hidden payload? | `inspect` |
| Every string in the DEX pools (not just referenced ones), with source DEX + index | `strings` |
| Pull one entry out (Hermes bundle, config blob, res XML) | `extract` |
| Read a compiled XML resource (network_security_config, backup rules, any res/xml) | `axml` |
| React Native / Hermes app: extract the bundle's actual strings/URLs | `hermes` (v59, v74..=96; `--pattern` for endpoints) |
| XAPK / split delivery: what does each member APK contain, base vs split | `xapk` |
| Resource names/values, lure text in `resources.arsc`, ID lookup | `resources` |
| Read a class's shape | `getclass` |
| Decompiled Java looks wrong (`getclass` warning) or you need exact bytecode/operands | `disasm` |
| Branch structure of a method (basic blocks + successors) / raw code units | `disasm --view cfg` / `disasm --view bytecode` (with `--method`) |
| What does method M call (and what do those call) | `calls --method M [--depth N]` |
| Exact signature / flags of method M (native? static? overloads?) | `member --method M` (callers: `findrefs method M --class C`) |
| Have the build's `mapping.txt`: what was obfuscated `a.b.c` / where did `Secret.charge` go | `mapping <mapping.txt> <needle>` |
| Which strings does one class use (URLs, keys, commands) | `strings --class C` |

## Output

- findrefs text: `dex | Lcaller/Class;->method | matched=(a; b)`, one line per caller method. `matched` for long regex strings can be huge; use `-o` and search the file, don't print raw.
- findrefs `--format json`: `{complete, matched_method_count, line_count, results:[{dex_name, complete, matches:[{caller, matched:[...]}]}]}`. Prefer json for post-processing.
- `--class` accepts `Lpkg/C;` or dotted. Exact by default; `--fuzzy-class` = substring.
- `getclass` prints decompiled Java (droidsaw backend): `// Source: X.java`, package, fields, and method bodies. Decompiled bodies can be imperfect; cross-check critical logic with `findrefs`.
- `getclass` stderr `warning: decompiled Java may be incorrect: N local(s) read but never assigned: v2_3, …` = the droidsaw structurer dropped a phi or emitted a use above its definition (name + order heuristic per method, stdout/JSON unchanged, exit code unchanged). A second warning (`M identical catch bodies`) fires when catch bodies are duplicated verbatim; the converged-handler variant (several guarded ranges whose handlers share one tail — verified on Locket's `MomentWidget.render`) instead shows up as the unbound-locals warning, so absence of the catch warning is not proof the Java is right. A third warning (`K loop(s) repeat a header statement at the start of the body`) flags droidsaw's loop rotation: the header's statements (typically `vN = it.hasNext();`) are emitted at BOTH ends of the `while` body, so the Java runs them twice per iteration while the bytecode runs them once — read the loop as if the first body statement were absent. It is a text heuristic (first top-level body statement == last); it fires on ~9 % of classes in the public corpus sample (54/600). `disasm` bypasses the structurer and is the ground-truth cross-check (see `crates/asc-decompile/BACKENDS.md` §11).
- `disasm` prints Smali-syntax (first line is a `#` note): `.class/.super/.source/.implements`, class `.annotation <build|runtime|system> Ltype; … .end annotation` blocks (`key = value` per element), `.field` (static initial values as ` = value`; a field with annotations gets them indented plus `.end field`), `.method … .end method` with `.registers`, `.param` blocks (debug name, `# Type` comment, parameter annotations + `.end param`; registers of the method frame, `pN` when the method has no code), then the method's annotations, instructions with debug directives (`.prologue`, `.epilogue`, `.line N`, `.local vN, "name":Type[, "sig"]`, `.end local`, `.restart local`, `.source`) before the instruction at their address, `:addr_<hex>` labels, `.catch/.catchall`, and `.packed-switch/.sparse-switch/.array-data` blocks at the method end (switch case targets are relative to the switch instruction, as the DEX spec says). R8/D8 release builds often encode the pc into `.line` (a `.line` before nearly every instruction, values unrelated to source lines) — that is the file's debug info, not a bug. A malformed annotation (or one nested deeper than 64) is printed as a `# annotation … unreadable: reason` comment a bad static initial value as `# static value unreadable: reason`, and an unreadable debug_info_item as `# debug info at 0x… unreadable: reason` (no debug directives for that method); the rest of the class still lists. Instruction registers are always `vN` (no `pN`), labels are `:addr_<hex>` — dialect differences from baksmali, not byte-identical. It does NOT go through the Java structurer, so it lacks the missing-assignment/duplicated-loop defects. `--method NAME` = exact name, every overload, fields omitted. It refuses instead of guessing: a method with an unknown opcode, bad payload, out-of-range pool reference or branch into the middle of an instruction fails the whole command with `Lcls;->name: code_item at 0x… pc N: reason` (exit 2). Exit `1` = class or method not found. Evidence: a 2,014-class sample of five corpus DEX (663,399 instructions) is byte-for-byte identical to androguard on every instruction, operand, label, directive and try item; debug directives and `.param` names were checked against androguard's debug_info parse with `tests/differential/run_debuginfo_diff.py`; `tests/differential/run_disasm_diff.py` exits 0 and reports only the 119 `payload_androguard` records where androguard's own parse of a damaged payload disagrees while the listing already matches the payload bytes. `invoke-custom`, `invoke-polymorphic`, `const-method-handle/type` are covered only by synthetic DEX (none in the corpus); no baksmali was available for byte comparison.
- `disasm --view bytecode` prints a per-instruction table (offset, code units, mnemonic, no resolved operands); `--view cfg` prints per-method basic blocks with successor edges. Same class/method lookup and exit codes as the Smali view.
- `calls` text: one line per edge `Lcaller;->m -> Lcallee;->member xN` (N = call sites in the caller body), indented two spaces per hop, then `# E edges, truncated: B, complete: B`. JSON: `{class, method, dex_names, edges:[{depth, from_class, from_member, to_class, to_member, sites, dex}], truncated, errors, complete}`. `truncated:true` = `--depth`/`--max-nodes` (default 200) cut the walk. Exit `1` = class not found; scan failures print the reachable part, warn on stderr and exit `2`.
- `member` text: one line per overload in declaration order (direct then virtual) `Lcls;->name(params)ret flags=0xHEX names…` (names from the DEX access bits, e.g. `public static native`; `volatile/bridge` and `transient/varargs` share a bit). JSON: `{class, method, overloads:[{descriptor, name, proto, flags, flag_names}]}`. Exit `1` = class not found or the class declares no method of that name (inherited methods are not listed).
- `mapping` text: one line per hit `original.Class[.member] -> mapped.Class[.member]`, classes first then members, file order. Needle = case-insensitive substring of original or obfuscated class/member names (a class needle also lists all its members). JSON: `{needle, hits:[{original_class, original_member, mapped_class, mapped_member}]}` (member fields empty for class hits). No hit = empty output + stderr count, exit `0`; unreadable file exit `1`. Lookup only (global `--mapping` translates class arguments and annotates findrefs/listclass/calls/member output); member signatures are dropped (overloads look alike).
- `strings --class C` text: `<dex> xN <text>` per distinct constant (first-encounter order) + `# complete:`; JSON `{class, dex_name, strings:[{text, sites}], total_matched, truncated, errors, complete}`. Only `const-string` loads in the class's own code are listed (not type/method names, not other classes). Exit `1` = class not found, `2` = partial scan.
- `listclass --with-dex`: prefixes every descriptor with its defining DEX (`classes.dex Lcom/x/Y;`; an `entry!classesN.dex` name marks a DEX-041 logical container — duplicate class names across DEXes stay distinguishable). JSON adds a parallel `class_dex` array. Default output (no flag) is unchanged.
- `extract` writes one entry to disk. Without `-o` the output name is the entry's **basename only** (traversal prefixes are stripped; basename-less names like `..` are refused with exit `1`), so entry names can never escape the cwd. `--verify-crc` re-checks the stored CRC-32 (exit `2` on mismatch — useful before treating a dumped entry as evidence). Exit `0` prints `extracted <entry> -> <path> (N bytes, method, crc)`.
- `cert` pair lines now classify each signing-block pair: `[signature]` (v2/v3/v3.1), `[source-stamp]` (0x2b09189e v1 / 0x6dff800d v2 — Play source stamps, not signer certs), `[padding]` (0x42726577 verity padding) and `[metadata]` (0x2146444e Google Play "frosting" protobuf — distribution metadata, NOT a signature). A Play-stamped APK therefore shows signature certs AND non-signature pairs; the `kind` field keeps them apart.
- `hermes` extracts the **structured string table** (per upstream `BytecodeFileFormat.h`) of every Hermes bundle in the APK: text lines `<bundle> #<index> <kind> <text>` where kind is `string`/`identifier`/`unknown`; JSON mirrors it with `supported`, `declared_string_count`, `identifier_count`. String-table lengths follow upstream semantics: UTF-16 entries are measured in UTF-16 code units (byte extent = length × 2), so non-ASCII strings decode fully; JSON and `--pattern` see the RAW decoded string (control characters included) — only the text renderer masks ASCII control chars/DEL as `·` to keep one line per string. Bytecode versions **59 and 74..=96** are decoded (layout checked against every tagged Hermes release: 59, 74, 76, 83, 84, 89, 96; v59's 2-bit string kinds are handled, `Predefined` reports as `identifier`); an untagged version inside that range decodes with a note that its layout is assumed. Any other version is reported `supported:false` + a note, strings are never guessed — fall back to `extract` + a raw `strings` pass. Entries are sniffed with a 36-byte prefix before any inflate, so huge non-Hermes assets never slow or fail the scan. Partial reports (unsupported version, decode failure, Hermes bundle over the 64 MiB cap) print what was decoded and exit `2`; the report-level `complete:false` says why. No bytecode is interpreted, no JS executed.
- `xapk` inventories a ZIP-of-APKs container member by member: `role=base|split|unknown` comes from each member's manifest `android:split` attribute ONLY (no manifest → `unknown`, never guessed from the filename); per-member manifest summary, per-DEX class counts (`error:` line per unreadable DEX) and `lib/<abi>` inventories stay separate — class/native-lib counts are NEVER summed across members, so "0 native libs in the base" is not "the app has none" when an ABI split is present. Oversized NON-DEX entries (huge assets) are skipped silently — they never appear as `dex` rows. Each member JSON carries `complete:false` + the header line ` (incomplete)` when its ZIP was unreadable or a DEX entry could not be read (cap/inflate); corrupt DEX *content* stays a per-DEX `error:` with the member still complete. Any incomplete member, unreadable member or cap-exceeded member is a warning + exit `2` (`complete:false` at report level). A 1 GiB aggregate work budget caps the total (declared + compressed) member bytes analyzed per container; exceeding it stops with `aggregate budget exceeded` + exit `2` (members already analyzed are still printed).
- `xapk` bounds total inflate work with an aggregate budget (default 1024 MiB; the library entry point can lower it). The budget is charged from each member's `declared uncompressed + compressed` size for a DEFLATE member (a stored member is charged its declared size only) **before** it is read and is never refunded, so a container full of malformed members still stops with `aggregate budget exceeded (<budget> MiB) before <member>; N of M members analyzed` — the message names the **actual** budget — and `complete:false` / exit `2`. Charging the compressed input too is what keeps the bound honest: a member may declare 0 uncompressed bytes and still make the decoder walk a whole payload. A member whose central-directory size lies (the DEFLATE stream expands past the declared size) is rejected **one byte** past that declared size — not after inflating the whole payload, and not after a whole 64 KiB chunk — so the declared size genuinely bounds the inflate work as well as the reservation.
- `inspect` per-DEX JSON now carries `coverage: "complete"|"partial"|"unknown"` (with the reason in `coverage_note`): `partial` = class walk died mid-DEX (counts are a lower bound), `unknown` = header/container never parsed (0 classes may mean 0 or anything). The manifest-vs-DEX cross-check adds `conclusive: bool` — when `false`, `components_missing_from_dex` counts components absent from a *partially scanned* DEX set; the text line prints `(inconclusive: DEX coverage partial)` and the `0/N components` anomaly says `not conclusive`. Never report a component as "missing" while `conclusive` is `false`.
- DEX-041 container entries: `inspect` JSON adds `container_members` (logical member count) and `container_size` (sum of member `file_size` fields). Checksums/SHA-1 are verified for **every** member; the size anomaly compares the members' declared sum with the physical entry (`container members sum to X != actual Y`), never member 0's `file_size` alone. `data_end`/`tail_bytes` stay unknown for containers (shared sections) — appended-payload detection does not apply to 041 entries.
- `axml` preserves **CDATA text nodes** in document order (children are `{"kind":"element",…}` / `{"kind":"text","text":"…"}` in JSON; text renders XML-escaped on its own line between the open/close tags). This is where `<domain>`/`<pin>`/`<certificates>` bodies of a `network_security_config.xml` live (verified on F-Droid `res/4u.xml` — 7 domains were previously invisible). Before trusting a "no domains" reading, check the text nodes, not just the elements.
- `manifest` permissions keep their **declaration type**: JSON `permissions[].decl` is `uses` / `uses-sdk-23` (from `<uses-permission-sdk-23>`/`-sdk-m>`) / `declares` (a custom `<permission>` the app defines). Text marks them `[sdk-23]` and `[declared, protectionLevel=…]`. The same permission name can appear twice (declared *and* used — e.g. AGP's `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`); that is two declarations, not a duplicate. `protectionLevel` is the raw attribute (often `0x…`); do not classify a permission as dangerous by name alone.
- Exit codes: `0` ok, `1` class not found / invalid input (including a malformed command line), `2` engine error. `findrefs` with zero hits prints nothing and exits `0` — but if any `classes*.dex` entry failed to scan, `findrefs` prints every hit it did find, warns per failing DEX on stderr and exits `2` (JSON keeps `complete:false` + `errors`). Check stdout *and* exit code, not just one.
- A `classes*.dex` entry whose bytes are **not a DEX** (bad magic — encrypted/scratch/packed payload) is a different case: it is skipped, not failed. `findrefs` still exits `0` and JSON keeps `complete:true`, but the skip is listed in `errors` and printed as `warning: … is not a DEX` on stderr. `strings` follows the same policy (skip warning on stderr, exit `0`, `complete:true`); a DEX that *parses* badly is the opposite — `strings` records it, flips `complete:false` and exits `2`. `listclass` skips silently (no errors field, no warning). `getclass` treats the class as simply not found (exit `1`) even when the APK contains other, real DEX files. So `complete:true` + exit 0 does **not** prove the whole APK was decoded — use `asc-rs inspect` to check every DEX's `class_count` / `coverage_note`, and read stderr.
- `--format json` for the other commands: `listclass` → `{total, per_dex:[{dex_name,count}], classes:[...]}`; `getclass` → `{dex_name, class_def_off, source}`; `disasm` → `{dex_name, class, method, view, listing}` (`listing` = the text output; `method` null without `--method`); `manifest` → the full structured manifest (`package`, `split`/`splitTypes`/…, `application` incl. `meta_data` and security booleans, `permissions` (with `max_sdk`), `uses_features`, `queries`, `activities`/`services`/`receivers` with `intent_filters[].{actions,categories,mime_groups,data,effective_data,auto_verify,priority}` + `meta_data`, `activity_aliases`, `providers`; absent values are `null`). Backward compatible: pre-existing keys kept; `exported` is the *effective* value (declared, else Android's filter/target-SDK inference), `exported_explicit` carries what the manifest actually declared, and `exported_state` is `explicit` | `legacy_inferred` | `missing_required` (the last = targetSdk>=31 + intent filter + no `android:exported`, an install-invalid manifest Android 12+ rejects). `intent_filters[].data` is the raw `<data>` list; `intent_filters[].effective_data` (`schemes`/`authorities`/`paths`/`mime_types` + `dependency`) is Android's **pooled** match set, and `dependency` (`complete` | `no_scheme` | `no_host`) says whether hosts/ports/paths are consulted at all. `intent_filters[].uri_relative_groups` holds API 35 `<uri-relative-filter-group>` children verbatim (`allow` + `data[].parts[]` of `{part: path|fragment|query, kind, value}`) — reported, **not** evaluated, so a non-empty list means the URI match surface is incomplete. Errors stay on stderr with the usual exit code (no JSON error body).
- `manifest` text: `package:`, `version:`, `sdk:`, optional `split:` line, `application:` block (declared values; `(default)` marks platform defaults, e.g. `allowBackup=true(default)`), `permissions`, `uses-features`, `queries`, then `activities`, `services`, `receivers`, `activity-alias`, `providers`. Components carry `[exported=true]`/`[exported=false]` when declared and `[exported=true(auto)]` when inferred from filters — `(auto)` is Android's inference, not a declaration. A filtered component with **no** `android:exported` while targeting API 31+ prints `[exported=? invalid: android:exported required for targetSdk>=31]` plus a `warning:` line: Android 12+ refuses to install that manifest, so the app never runs on a modern device. Filters print `action`/`category` lines, a `group <name>` line per mime-group child, and one `match: schemes=[…] authorities=[…] paths=[…] mimeTypes=[…]` line: Android pools **every** `<data>` element of a filter per attribute dimension (a scheme in one `<data>` matches a host in another) — when the filter has more than one `<data>` the line says `(pooled across <data> elements: every dimension is matched independently)`. But pooling is not a blank cheque: `scheme` and `host` are looked for across the whole filter, so a declared host without a scheme and a declared path without scheme+host are **inert** — the line then prints `[declared but ignored by Android: … — no android:host is declared, so ports and paths are ignored]` (or the `no android:scheme` variant) instead of presenting them as active restrictions. A MIME type with no scheme adds `(MIME type without a scheme: content: and file: URIs also match)`. API 35 `<uri-relative-filter-group>` children print as `uri-relative-filter-group allow=…: …` lines followed by `warning: <uri-relative-filter-group> (API 35) is reported as declared and NOT evaluated — this filter's URI match surface is incomplete`; that warning means the file needs a hand read, not that the filter is fully modelled. Never read `data …` per element as independent URIs. `meta-data:` lines print `name = value` / `resource=@0x…`. It tolerates the manifest tampering Android itself ignores (zeroed root chunk type, garbage string-pool slots, garbage chunks after `</manifest>`), and non-Android namespaces (`tools:`, `dist:`) never alias android: attributes. Exit `2` = the manifest really is unparseable (or absent).
- `manifest --match-uri <uri>` evaluates the API 35 `<uri-relative-filter-group>` path/group layer of every activity / activity-alias / service / receiver filter (text and JSON cover the same scope) against a concrete URI, replacing each filter's "NOT evaluated" warning with a **three-valued verdict**: `matches` / `cannot match` / `unknown`, each with the assumed platform flag (`assumed flag=on` = the group feature enabled) and a reason. It assesses only the URI/data layer — it does **not** model full Intent resolution, `android:exported` reachability, App Links verification, categories or MIME types, so a `matches` here is not a claim the component is reachable. Text prints a `match-uri <uri>: <verdict> (assumed flag=…)` line per filter; JSON adds an additive top-level `uri_match` report (`uri`, `assumed_flag_on`, `results[{kind, component, filter_index, verdict, reasons}]`) beside all pre-existing manifest keys (`kind` = activity/activity_alias/service/receiver, additive). Rules: filter-level paths are ORed with the groups; a scheme+host filter with **no** path matcher (and no group, flag on) matches at the authority level (`authMatch`); group matchers are ANDed per group and consulted in declaration order, the first matching group deciding by its `allow` flag; an empty group never matches; groups are consulted only after a scheme+host match; query applies the matcher's kind per `&`-then-`;`-split parameter (`+` is a literal character); a declared host that does not match the URI (case-insensitive, `*`-suffix wildcards, numeric port) is a definite `cannot match`. `unknown` (with a reason, never a guessed match) when the semantics are not oracle-confirmed yet — **`pathPattern`/`pathAdvancedPattern` glob matchers** —, when the filter declares no scheme/host (group layer inert), when an opaque/no-`://` URI or a group/data/matcher count above the caps (64/64/256) would need truncation, or when an earlier uncertain group could flip a later ordered decision. Do not present an `unknown` as reachable.
- `--paranoid`: use when `getclass` shows `long v = -123…L; X.y(v)` pairs (a static `(J)String` call) or `findrefs string` misses text you know exists. `getclass` then shows the decoded literals; `findrefs string` also matches decoded values. Only ids that are a `const-wide` in the same basic block get decoded; other calls stay as-is. The output is rewritten bytecode, not the original. Say so when you quote it.

- `--decode-xor`: use when strings in the sample are hidden as `byte[] a = {8, 7, …}; X.i(a)` (a static `([B)String` decoder that XORs every element with a literal key) — common in packer stubs (verified on a Virbox sample). `findrefs string` also matches decoded values; `getclass` replaces provable calls with the decoded literal (the array-building code stays as dead code). Only sites proven on **every** path are patched: the key must be a literal or an `sget` of a `static final` int field declared in the same DEX whose value is its encoded initializer (no writes) or a constant stored by the one write, made in straight-line `<clinit>` code that only loads constants before it, all elements constant (`const`+`aput-byte` chains or `fill-array-data`), the bytes valid UTF-8, and no alias of the array read after the call (the decoder mutates in place). Unprovable sites stay as-is — absence of a decode is not evidence of a hidden string. Like `--paranoid`, the output is rewritten bytecode, not the original.

## Workflow

1. Malware/unknown sample: start with `manifest` (permissions + exported components/receivers are your first IOCs), then `listclass <apk>` → file, then filter for candidates (obfuscated APKs: search by package/pattern).
2. `findrefs` with the narrowest predicate (`--class` + name beats name alone). Matching is substring: short names (`get`, `http`) flood results.
3. `getclass` on interesting callers/classes.
4. Redirect big output: `-o out.txt` (findrefs appends; `listclass`, `manifest`, `inspect`, `native` and `cert` overwrite and print nothing to stdout).

## Signing certificates (`cert`)

Lists JAR v1 (`META-INF/*.RSA|DSA|EC`) and APK Signature Scheme v2/v3/v3.1 signers with SHA-256/SHA-1 fingerprints, subject/issuer/serial/validity, algorithm IDs (full `u32`) and the v3 SDK range. **v1, v2, v3 and v3.1 signers are verified** (report `verification` = `v1`, `v2_v3`, `v1_v2_v3`, or `not_performed` when no signer exists): each signer gets `verification.status` = `verified` (>=1 signature and the content digest checked, nothing failed), `failed`, or `unsupported` (nothing failed but no signature or no content digest could be checked), plus one `ok:`/`FAIL:`/`skip:` line per check — every signature over the signed data (RSA-PSS/PKCS#1 SHA-256/512, ECDSA P-256/P-384; DSA and keys the RSA crate refuses, e.g. >4096 bit, are `skip`), signed key == first certificate's SubjectPublicKeyInfo, digest and signature algorithm lists equal, v3 signed/unsigned SDK range equal, and the chunked SHA-256/512 content digest over the whole archive (verity 0x0421/0x0423 digests are `skip`, not computed). Each **v1** signer (`META-INF/X.RSA|EC|DSA`) is checked like `apksig`: the PKCS#7 signature over `X.SF` (direct, or via signed attributes whose messageDigest must match; RSA PKCS#1 SHA-1/256/384/512 and ECDSA P-256/P-384, DSA/RSA-PSS = `skip` → `unsupported`), `X.SF`'s whole-`MANIFEST.MF` digest (else main-attributes + every per-entry section), and every ZIP entry's `MANIFEST.MF` digest; a missing/mismatched entry, an entry not listed in `MANIFEST.MF` (files added after signing; `META-INF/` signature files excepted), or duplicate ZIP names make it `failed` (mismatch lines capped at 20 per kind; entries >256 MiB are `skip`). **Not checked**: the v1 `X-Android-APK-Signed` stripping header, rotation proofs (v3 lineage), stripping protection, certificate chains, validity dates, revocation, trust. A `failed` signer means tampering or a broken signature, but exit code stays `0`: read the status, not the exit code. `verified` proves integrity under that key, never who owns the key. Roles: `signer` is the first v2/v3 certificate or the v1 certificate matching the SignerInfo issuer+serial; the rest are `chain`, or `unmatched` if the v1 signer cannot be identified. Scheme equality is stated only when SHA-256 sets match; differences are shown (not an error). Unknown signing-block pair IDs are listed verbatim. `subject == issuer` is shown but never claimed as self-signed. Subjects print in encoded order (openssl `-nameopt RFC2253` prints reversed). `no signing material found` does not mean unsigned/valid. Malformed signing data prints the partial report and exits `2`, as does a raw `.dex` or unreadable input; ZIP64 archives report the signing block as `unsupported` (scheme status `unknown`).

## Resource table (`resources`)

Reads `resources.arsc`: without filters it prints packages, entry/config counts and per-type counts. `--id 0x7f020000` lists every config variant of that ID (ID = package<<24 | (type+typeIdOffset)<<16 | entry index; the key-string index is a different field). `--strings PAT` is a case-sensitive substring over key names (`matched=key`) and string values (`matched=value`, including bag items); `--limit N` (default 100) caps printed hits, `matches:` still shows the total. `TYPE_STRING` values come from the table's global pool; references print as raw `@0x…` IDs (system `0x01…` included, never resolved). A `res/…` value is the path the table claims, not proof the file is a valid resource. Config text is `default` or locale/dpi/vNN plus `raw=<hex>`. No `resources.arsc` entry: text says so, exit `0`. Undecodable string slots read as empty and are noted in `diagnostic:` lines; a malformed chunk is skipped (the walk never guesses the next chunk), the report says `INCOMPLETE` and the exit code is `2`. Raw DEX or an unparseable table exits `2`. Values are display strings and not aapt2-equivalent; compact/sparse/offset16 layouts follow AOSP but are only synthetic-tested (the corpus has dense layouts, package `0x7f`).

## Native libraries (`native`)

Scans `lib/**.so` and `assets/**.so` (in memory, never written to disk; 64 MiB cap each) and every native method (`ACC_NATIVE`) in both direct and virtual lists of all DEX (including DEX-041 members). Methods are joined to libs by JNI symbol name (short and long form). Each lib is also scanned for static `JNINativeMethod {name, signature, fnPtr}` arrays (the `RegisterNatives` input) in non-executable `PT_LOAD` data: text lines `  jni-table <name> <sig> -> <addr|<symbol>>`, JSON `jni_table`; pointers resolve through `R_*_RELATIVE` (`DT_RELA` or Android packed `DT_ANDROID_RELA`, APS2) or the in-file word (`DT_REL`/`DT_ANDROID_REL`/`DT_RELR`), fnPtr must land in an executable segment (Thumb bit cleared) or be a symbolic relocation (`<symbol>`). A method whose name + descriptor appear in a table gets `table-match: <libs>` (JSON `table_libs`) — the table does not name the class, so this is a candidate too. A malformed or truncated APS2 stream keeps what decoded and marks the lib `[INCOMPLETE]` with a note. Every match is a *candidate* link, not proof. `unbound` = neither a `Java_*` export nor a table entry: registration from run-time data (tables built or strings decrypted in `JNI_OnLoad`) is still possible and NOT detected. `abi_dir` is reported next to `e_machine` and can disagree (`MISMATCH`). Symbol table comes from section headers, else `PT_DYNAMIC`; `symbol_source: none` or `[INCOMPLETE]` means exports are unknown, not zero. Split APKs (`config.*.apk`) carry libs but no DEX: pair them with the base APK by hand. Both `--format json` and text list every native method.

## Packed APKs

`asc-rs inspect` automates the checks below. `packer: virbox` needs >= 2 independent Virbox signals (stub class `Lv<hex>/l<hex>;`, `assets/l<hex>_{a32,a64,x86,x64}.so` family, the string "Virbox"). Other packers are NOT identified (no rule verified yet): `packer: none identified` does not mean unpacked. "tail bytes" = bytes past what the DEX map declares; it is only reported when the map gives an exact extent (`coverage unknown` otherwise, and never read as 0) and is an appended-payload *candidate*, not proof. Entropy is from a <=1 MiB prefix and unverified. `--format json` gives the full per-entry inventory; text lists only dex/elf/zip entries.

`inspect` memory: it reads every `classes*.dex` byte (checksum, SHA-1, Virbox string scan) plus up to 1 MiB of each entry for entropy. On STORED APKs those are mmap page touches, so its peak working set grows with DEX size (measured ~83 MiB on a 76.6 MiB APK with 53 MiB of STORED DEX) while private memory stays ~8-10 MiB (`read_bytes = 0`; clean file-backed pages, reclaimable). Other commands touch far less (`cert`/`manifest`/`resources` ~5-15 MiB on the same file). Do not read a large working set as a leak.

Suspect a packer when `listclass` returns only a few classes but `classes.dex` is large (MBs), and manifest components (e.g. `…LoginActivity`) are missing from `listclass`. The real DEX is encrypted and appended to or hidden beside a stub; no static tool (asc-rs or jadx) can see it.
- Virbox signs: stub classes `Lv<hex>/l<hex>;` (+ `$inner`), the string `"Virbox"` (`findrefs string Virbox`), native methods `I<hex>_00…05`, `assets/l<hex>_{a32,a64,x86,x64}.so`.
- Report only the stub + manifest as analysed; say the payload was not. Next step: runtime dump (BlackDex / frida-dexdump), then run asc-rs on the dumped DEX (zip it as `classes.dex` in an APK).

## asc-rs vs jadx class counts

`listclass` lists only classes defined in `classes*.dex` (what ART loads). jadx also shows nodes for components declared in the manifest (even when no DEX defines them) and for embedded Java class files (e.g. `DebugProbesKt.bin`, magic `CAFEBABE` → `kotlin.coroutines.jvm.internal`). jadx showing more is expected, not an asc-rs bug. Use `manifest` to see declared-but-absent components.

## Pitfalls

- `findrefs extends|impl` reads only class definitions in the APK, so the match is on the exact descriptor and framework classes in between are invisible: `extends android.app.Activity` misses an app class whose parent is `androidx…AppCompatActivity` unless you pass `--transitive` (which walks APK-defined classes only). `impl` (direct) lists classes that name the interface themselves; inheriting it via a superclass or sub-interface needs `--transitive`. Output `<dex> | <class>`, with `    # via <parent>` on depth > 1; no hits is exit 0 plus a stderr note. JSON: `hits[]{dex,class,depth,via}` plus `complete`/`errors`. A class row that fails to decode is reported (exit 2) and its subtree is lost, so `--transitive` hits are a lower bound on an incomplete scan; a DEX whose rows share lists so much that work would exceed its byte size is cut off the same way ("work budget exhausted").
- `listmethod` lists methods *defined* (class_data, direct then virtual), not called; `--name` is a case-insensitive substring, `--class` an exact class (unknown class = exit 1). Over `--limit` (default 100000) the text ends with a `... truncated` line and JSON has `truncated: true`. JSON: `methods[]{dex,class,name,proto,flags}`, `total_matched` (all matches, not only the listed ones), `truncated`, `complete`, `errors`; an incomplete scan exits 2.

- On Windows, piping to `head` prints a harmless "pipe has been ended" panic; use `-o` and read the file.
- On Windows, paths with non-ASCII characters (e.g. Vietnamese file names) can make captured stdout come back empty. Use `-o FILE` and read the file (set `PYTHONIOENCODING=utf-8` if a Python helper prints).
- Constructors/static init are `<init>` / `<clinit>`.
- Multidex is automatic (`classes*.dex` numeric order); `dex_name` says which.
- A process-wide 2 GiB budget caps DEX bytes held by concurrent `getclass`/`disasm`/`findrefs` scans. An APK large enough to hit it fails with `memory budget exceeded` (exit `2`; `findrefs` records it per DEX and still exits `2` with partial output) — that means the input is pathological for this machine, not that the tool is broken.
- `calls --method NAME` exits `1` (`Method NAME not found in class.`) when the class declares no method of that name; an empty tree with exit `0` means the method exists but invokes nothing (or is abstract/native). Callees outside the APK (framework/library) are leaves: they appear as edges but are never expanded.
- The **CLI** never rewrites names in place: `--mapping` only appends originals next to obfuscated names (findrefs/listclass/calls/member), and `getclass`/`disasm` source stays obfuscated — don't present it as de-obfuscated. Original names come from a mapping file you supplied; a stale mapping gives wrong names. CFG, bytecode table and call tree are available in the CLI (`disasm --view`, `calls`).
- **Deep links / intent filters: never treat each `<data>` element as an independent URI.** Android pools every `<data>` of one `<intent-filter>` per attribute dimension, so a scheme in one element matches a host in another — `manifest` prints one pooled `match:` line per filter for exactly this reason. A filter reading `scheme=https host=a.example.com` + `scheme=myapp host=b.example.com` also matches `https://b.example.com` and `myapp://a.example.com`. The dimensions are **dependent** though: with no `scheme` anywhere, hosts, ports and paths are ignored outright; with a scheme but no `host`, ports and paths are ignored (`IntentFilter.matchData` nests the authority loop inside `schemes != null` and the path loop inside the authority branch). Such inert attributes are still printed, labelled `[declared but ignored by Android: …]` — do not report them as reachable URLs. A `mimeType` with no scheme instead matches intents carrying no URI plus `content:`/`file:` URIs (not `http`/`https`). API 35 `<uri-relative-filter-group>` (ANDed, allow/deny-ordered, evaluated after sibling `<data>`) is reported **raw and unevaluated**, with a `warning:` line: for those filters the printed match set is incomplete, so read the manifest entry by hand before concluding which deep links are reachable.
- A component with an intent filter and no `android:exported` while the app targets API 31+ is an **invalid manifest**: Android 12+ refuses to install it. `manifest` prints `[exported=? invalid: …]` and a `warning:` line — do not report such a component as a working exported entry, and do not silently "fix" it to `exported=false`.
- API 35 `<uri-relative-filter-group>`: only **Android-namespaced (or unqualified)** `path*`/`fragment*`/`query*` attributes are read as matchers on its `<data>` children; a foreign namespace with a colliding local name (`tools:path`, a custom `NS:pathPrefix`) is ignored, mirroring every other manifest attribute. Plain `manifest` (no `--match-uri`) still reports the groups raw with a `NOT evaluated` warning — that alone never claims to model its AND/allow/deny matching. `manifest --match-uri <uri>` does evaluate them, but its verdicts are only as strong as what the platform proofs cover: `pathPattern`/`pathAdvancedPattern` are evaluated too (a port of `android.os.PatternMatcher`: `\` escapes, `.`, `X*`, `[..]`, `{n,m}`), a filter that declares a `mimeType` is `cannot_match` (matching runs with a null intent type, and `findMimeType(null)` is false; an `android:mimeGroup` reference is not read at all and adds no dimension — it only matters for the wildcard `matchData` variant), a scheme-only filter matches at the scheme level with its paths and groups ignored, group/data/matcher counts are never truncated, and a malformed `%` escape decodes to `U+FFFD` instead of `unknown` — those are the only sources of `unknown` left besides an opaque (no `://`) or over-1 MiB URI with no path matcher (and no group, flag on) matches at the authority level (`authMatch`) even for an unrelated path, host matching is case-insensitive with leading-`*` suffix wildcards, ports compare numerically, userinfo is stripped, `opaque`/no-`://` URIs return `unknown`. A URI part with a **malformed percent-escape** (a truncated `%`/`%A`, or a non-hex `%GG`) or bytes that are not valid UTF-8 after decoding is decided by `UriCodec` semantics, never an `unknown` and never a panic. A hierarchical URI with no path has an **empty path `""`** (matching `path=""`/`pathPrefix=""`; distinct from the root `"/"`), and a `\` ends the authority and is **kept in the path** (`https://example.com\private` → host `example.com`, path `\private`). Do not read an `unknown` verdict as reachable.
  A filter-level `<group android:name>` (mime group) is echoed as a `group <name>` line and JSON `mime_groups`, but the platform reads the names only in the wildcard `matchData` variant, so they never change a `--match-uri` verdict; no aapt2 build compiles the element, so hand-built AXML is the only source.
- Smoke-test on any small APK you have; verify the binary runs with `asc-rs --help` before relying on it.
