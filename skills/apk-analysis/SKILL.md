# Using asc-rs (APK analysis CLI)

Binary: `asc-rs` (Windows: `asc-rs.exe`) — a standalone prebuilt executable, no JVM/Python/Rust toolchain needed. If `asc-rs` is not on PATH, locate the shipped binary in the environment rather than building anything. Lazy, on-demand; no preprocessing. Run `asc-rs <cmd> --help` for flags.

## Commands

```
asc-rs findrefs <apk> string <substr>            # callers of a string-pool match
asc-rs findrefs <apk> type   <substr>            # callers referencing a type descriptor
asc-rs findrefs <apk> method [name] [--class C [--fuzzy-class]]
asc-rs findrefs <apk> field  [name] [--class C [--fuzzy-class]]
asc-rs getclass <apk> <Lpkg/Cls; | pkg.Cls>      # decompile ONE class
asc-rs disasm <apk> <Lpkg/Cls; | pkg.Cls> [--method NAME]   # Smali-syntax listing of ONE class (bytecode, not Java)
asc-rs listclass <apk> [-o FILE]                 # all class descriptors, DEX order
asc-rs manifest <apk> [-o FILE]                  # full manifest: package, split markers, application attrs + meta-data, permissions (maxSdk), uses-features, queries, components with deep-link data/aliases
asc-rs inspect <apk|dex> [-o FILE]               # entry inventory (incl. Hermes bundles), DEX coverage/checksums, packer signals, split-APK status, manifest-vs-DEX check
asc-rs native  <apk|dex> [-o FILE]               # lib/ + assets/*.so ELF inventory, DEX native methods, JNI export name match; notes missing ABI splits
asc-rs cert    <apk> [-o FILE]                   # signing certs: JAR v1 + APK Signature Scheme v2/v3 (display only, NOT verified)
asc-rs resources <apk> [--id 0x7f020000 | --strings PAT] [--limit N] [-o FILE]   # resources.arsc inventory / lookup / search
asc-rs strings <apk|dex> [--substring PAT] [--limit N] [-o FILE]   # every DEX string-pool entry (multidex + DEX-041), with source DEX + index
asc-rs extract <apk> <entry> [-o FILE] [--verify-crc]   # pull one entry out (safe basename by default, optional CRC check)
asc-rs axml    <apk> <entry> [-o FILE]           # decode any compiled binary-XML entry (res/xml/*, manifest) to text/JSON
asc-rs hermes  <apk> [--pattern PAT] [--limit N] [-o FILE]   # structured string-table extraction from Hermes bundles (v96 only; other versions reported unsupported)
asc-rs xapk    <file.xapk> [-o FILE]             # XAPK container inventory: member APKs (manifest, DEX class counts, native libs) analyzed per member, never merged
Input: an APK/ZIP **or a bare `.dex`** (DEX 035..041; e.g. a runtime-dumped DEX). A bare DEX is one virtual entry named after the file: `manifest`, `cert`, `resources` on it exit `2` ("requires an APK"); `extract`/`axml` on a missing entry exit `1`, on the dex-named entry `extract` exits `0` (raw bytes) and `axml` exits `2` (a DEX is not binary XML); an unparseable or CDEX/ODEX/VDEX file exits `2` with a clear error instead of empty output.
Shared flags (any position): `-o FILE`, `--threads N` (default 8), `--debug` (timings to stderr), `--format text|json` (all commands), `--paranoid` (decode Paranoid/LSParanoid strings; off by default), `--decode-xor` (decode const-array XOR strings; off by default).

## Choosing the command

| Goal | Use |
|---|---|
| Who uses URL / key / log text | `findrefs string` |
| Who calls API X (e.g. `getSystemService`) | `findrefs method X` |
| Who calls anything on class C | `findrefs method --class C` (no name) |
| Who touches a field | `findrefs field` |
| Who references a type (e.g. `Ljava/lang/StringBuilder;`) | `findrefs type` |
| Class name unknown | `listclass`, filter output, then `getclass` |
| Package, permissions, exported components (declared vs inferred vs **install-invalid**), receivers, deep links (pooled `scheme`/`host`/`path` match set + inert-dimension flags + API 35 `<uri-relative-filter-group>` warning — see Pitfalls), meta-data, split markers | `manifest` |
| Is this sample packed / is there hidden payload? | `inspect` |
| Every string in the DEX pools (not just referenced ones), with source DEX + index | `strings` |
| Pull one entry out (Hermes bundle, config blob, res XML) | `extract` |
| Read a compiled XML resource (network_security_config, backup rules, any res/xml) | `axml` |
| React Native / Hermes app: extract the bundle's actual strings/URLs | `hermes` (v96; `--pattern` for endpoints) |
| XAPK / split delivery: what does each member APK contain, base vs split | `xapk` |
| Resource names/values, lure text in `resources.arsc`, ID lookup | `resources` |
| Read a class's shape | `getclass` |
| Decompiled Java looks wrong (`getclass` warning) or you need exact bytecode/operands | `disasm` |

## Output

- findrefs text: `dex | Lcaller/Class;->method | matched=(a; b)`, one line per caller method. `matched` for long regex strings can be huge; use `-o` and search the file, don't print raw.
- findrefs `--format json`: `{complete, matched_method_count, line_count, results:[{dex_name, complete, matches:[{caller, matched:[...]}]}]}`. Prefer json for post-processing.
- `--class` accepts `Lpkg/C;` or dotted. Exact by default; `--fuzzy-class` = substring.
- `getclass` prints decompiled Java (droidsaw backend): `// Source: X.java`, package, fields, and method bodies. Decompiled bodies can be imperfect; cross-check critical logic with `findrefs`.
- `getclass` stderr `warning: decompiled Java may be incorrect: N local(s) read but never assigned: v2_3, …` = the droidsaw structurer dropped a phi (name heuristic, stdout/JSON unchanged, exit code unchanged). A second warning (`M identical catch bodies`) fires when catch bodies are duplicated verbatim; the converged-handler variant (several guarded ranges whose handlers share one tail — verified on Locket's `MomentWidget.render`) instead shows up as the unbound-locals warning, so absence of the catch warning is not proof the Java is right. `disasm` bypasses the structurer and is the ground-truth cross-check (see `crates/asc-decompile/BACKENDS.md` §11).
- `disasm` prints Smali-syntax (first line is a `#` note): `.class/.super/.implements`, `.field`, `.method … .end method` with `.registers`, instructions, `:addr_<hex>` labels, `.catch/.catchall`, and `.packed-switch/.sparse-switch/.array-data` blocks at the method end (switch case targets are relative to the switch instruction, as the DEX spec says). Not emitted: annotations, static initial values, debug info (`.line/.local/.param`). Registers are always `vN` (no `pN`), labels are `:addr_<hex>` — dialect differences from baksmali, not byte-identical. It does NOT go through the Java structurer, so it lacks the missing-assignment/duplicated-loop defects. `--method NAME` = exact name, every overload, fields omitted. It refuses instead of guessing: a method with an unknown opcode, bad payload, out-of-range pool reference or branch into the middle of an instruction fails the whole command with `Lcls;->name: code_item at 0x… pc N: reason` (exit 2). Exit `1` = class or method not found. Evidence: a 2,014-class sample of five corpus DEX (663k instructions) has 0 mnemonic and 0 try/catch mismatches vs androguard and 4 formatting-only operand reports; `tests/differential/run_disasm_diff.py` still exits 1 on ~15 methods it attributes to oracle/runner payload-tail handling (2 spot-checked as fine, the rest not individually reviewed). `invoke-custom`, `invoke-polymorphic`, `const-method-handle/type` are covered only by synthetic DEX (none in the corpus); no baksmali was available for byte comparison.
- `listclass --with-dex`: prefixes every descriptor with its defining DEX (`classes.dex Lcom/x/Y;`; an `entry!classesN.dex` name marks a DEX-041 logical container — duplicate class names across DEXes stay distinguishable). JSON adds a parallel `class_dex` array. Default output (no flag) is unchanged.
- `extract` writes one entry to disk. Without `-o` the output name is the entry's **basename only** (traversal prefixes are stripped; basename-less names like `..` are refused with exit `1`), so entry names can never escape the cwd. `--verify-crc` re-checks the stored CRC-32 (exit `2` on mismatch — useful before treating a dumped entry as evidence). Exit `0` prints `extracted <entry> -> <path> (N bytes, method, crc)`.
- `cert` pair lines now classify each signing-block pair: `[signature]` (v2/v3/v3.1), `[source-stamp]` (0x2b09189e v1 / 0x6dff800d v2 — Play source stamps, not signer certs), `[padding]` (0x42726577 verity padding) and `[metadata]` (0x2146444e Google Play "frosting" protobuf — distribution metadata, NOT a signature). A Play-stamped APK therefore shows signature certs AND non-signature pairs; the `kind` field keeps them apart.
- `hermes` extracts the **structured string table** (per upstream `BytecodeFileFormat.h`) of every Hermes bundle in the APK: text lines `<bundle> #<index> <kind> <text>` where kind is `string`/`identifier`/`unknown`; JSON mirrors it with `supported`, `declared_string_count`, `identifier_count`. String-table lengths follow upstream semantics: UTF-16 entries are measured in UTF-16 code units (byte extent = length × 2), so non-ASCII strings decode fully; JSON and `--pattern` see the RAW decoded string (control characters included) — only the text renderer masks ASCII control chars/DEL as `·` to keep one line per string. Only bytecode **version 96** is decoded; any other version is reported `supported:false` + a note, strings are never guessed — fall back to `extract` + a raw `strings` pass. Entries are sniffed with a 36-byte prefix before any inflate, so huge non-Hermes assets never slow or fail the scan. Partial reports (unsupported version, decode failure, Hermes bundle over the 64 MiB cap) print what was decoded and exit `2`; the report-level `complete:false` says why. No bytecode is interpreted, no JS executed.
- `xapk` inventories a ZIP-of-APKs container member by member: `role=base|split|unknown` comes from each member's manifest `android:split` attribute ONLY (no manifest → `unknown`, never guessed from the filename); per-member manifest summary, per-DEX class counts (`error:` line per unreadable DEX) and `lib/<abi>` inventories stay separate — class/native-lib counts are NEVER summed across members, so "0 native libs in the base" is not "the app has none" when an ABI split is present. Oversized NON-DEX entries (huge assets) are skipped silently — they never appear as `dex` rows. Each member JSON carries `complete:false` + the header line ` (incomplete)` when its ZIP was unreadable or a DEX entry could not be read (cap/inflate); corrupt DEX *content* stays a per-DEX `error:` with the member still complete. Any incomplete member, unreadable member or cap-exceeded member is a warning + exit `2` (`complete:false` at report level). A 1 GiB aggregate work budget caps the total (declared + compressed) member bytes analyzed per container; exceeding it stops with `aggregate budget exceeded` + exit `2` (members already analyzed are still printed).
- `xapk` bounds total inflate work with an aggregate budget (default 1024 MiB; the library entry point can lower it). The budget is charged from each member's `declared uncompressed + compressed` size for a DEFLATE member (a stored member is charged its declared size only) **before** it is read and is never refunded, so a container full of malformed members still stops with `aggregate budget exceeded (<budget> MiB) before <member>; N of M members analyzed` — the message names the **actual** budget — and `complete:false` / exit `2`. Charging the compressed input too is what keeps the bound honest: a member may declare 0 uncompressed bytes and still make the decoder walk a whole payload. A member whose central-directory size lies (the DEFLATE stream expands past the declared size) is rejected **one byte** past that declared size — not after inflating the whole payload, and not after a whole 64 KiB chunk — so the declared size genuinely bounds the inflate work as well as the reservation.
- `inspect` per-DEX JSON now carries `coverage: "complete"|"partial"|"unknown"` (with the reason in `coverage_note`): `partial` = class walk died mid-DEX (counts are a lower bound), `unknown` = header/container never parsed (0 classes may mean 0 or anything). The manifest-vs-DEX cross-check adds `conclusive: bool` — when `false`, `components_missing_from_dex` counts components absent from a *partially scanned* DEX set; the text line prints `(inconclusive: DEX coverage partial)` and the `0/N components` anomaly says `not conclusive`. Never report a component as "missing" while `conclusive` is `false`.
- DEX-041 container entries: `inspect` JSON adds `container_members` (logical member count) and `container_size` (sum of member `file_size` fields). Checksums/SHA-1 are verified for **every** member; the size anomaly compares the members' declared sum with the physical entry (`container members sum to X != actual Y`), never member 0's `file_size` alone. `data_end`/`tail_bytes` stay unknown for containers (shared sections) — appended-payload detection does not apply to 041 entries.
- `axml` preserves **CDATA text nodes** in document order (children are `{"kind":"element",…}` / `{"kind":"text","text":"…"}` in JSON; text renders XML-escaped on its own line between the open/close tags). This is where `<domain>`/`<pin>`/`<certificates>` bodies of a `network_security_config.xml` live (verified on F-Droid `res/4u.xml` — 7 domains were previously invisible). Before trusting a "no domains" reading, check the text nodes, not just the elements.
- `manifest` permissions keep their **declaration type**: JSON `permissions[].decl` is `uses` / `uses-sdk-23` (from `<uses-permission-sdk-23>`/`-sdk-m>`) / `declares` (a custom `<permission>` the app defines). Text marks them `[sdk-23]` and `[declared, protectionLevel=…]`. The same permission name can appear twice (declared *and* used — e.g. AGP's `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`); that is two declarations, not a duplicate. `protectionLevel` is the raw attribute (often `0x…`); do not classify a permission as dangerous by name alone.
- Exit codes: `0` ok, `1` class not found / invalid input, `2` engine error. `findrefs` with zero hits prints nothing and exits `0` — but if any `classes*.dex` entry failed to scan, `findrefs` prints every hit it did find, warns per failing DEX on stderr and exits `2` (JSON keeps `complete:false` + `errors`). Check stdout *and* exit code, not just one.
- A `classes*.dex` entry whose bytes are **not a DEX** (bad magic — encrypted/scratch/packed payload) is a different case: it is skipped, not failed. `findrefs` still exits `0` and JSON keeps `complete:true`, but the skip is listed in `errors` and printed as `warning: … is not a DEX` on stderr. `strings` follows the same policy (skip warning on stderr, exit `0`, `complete:true`); a DEX that *parses* badly is the opposite — `strings` records it, flips `complete:false` and exits `2`. `listclass` skips silently (no errors field, no warning). `getclass` treats the class as simply not found (exit `1`) even when the APK contains other, real DEX files. So `complete:true` + exit 0 does **not** prove the whole APK was decoded — use `asc-rs inspect` to check every DEX's `class_count` / `coverage_note`, and read stderr.
- `--format json` for the other commands: `listclass` → `{total, per_dex:[{dex_name,count}], classes:[...]}`; `getclass` → `{dex_name, class_def_off, source}`; `manifest` → the full structured manifest (`package`, `split`/`splitTypes`/…, `application` incl. `meta_data` and security booleans, `permissions` (with `max_sdk`), `uses_features`, `queries`, `activities`/`services`/`receivers` with `intent_filters[].{actions,categories,data,effective_data,auto_verify,priority}` + `meta_data`, `activity_aliases`, `providers`; absent values are `null`). Backward compatible: pre-existing keys kept; `exported` is the *effective* value (declared, else Android's filter/target-SDK inference), `exported_explicit` carries what the manifest actually declared, and `exported_state` is `explicit` | `legacy_inferred` | `missing_required` (the last = targetSdk>=31 + intent filter + no `android:exported`, an install-invalid manifest Android 12+ rejects). `intent_filters[].data` is the raw `<data>` list; `intent_filters[].effective_data` (`schemes`/`authorities`/`paths`/`mime_types` + `dependency`) is Android's **pooled** match set, and `dependency` (`complete` | `no_scheme` | `no_host`) says whether hosts/ports/paths are consulted at all. `intent_filters[].uri_relative_groups` holds API 35 `<uri-relative-filter-group>` children verbatim (`allow` + `data[].parts[]` of `{part: path|fragment|query, kind, value}`) — reported, **not** evaluated, so a non-empty list means the URI match surface is incomplete. Errors stay on stderr with the usual exit code (no JSON error body).
- `manifest` text: `package:`, `version:`, `sdk:`, optional `split:` line, `application:` block (declared values; `(default)` marks platform defaults, e.g. `allowBackup=true(default)`), `permissions`, `uses-features`, `queries`, then `activities`, `services`, `receivers`, `activity-alias`, `providers`. Components carry `[exported=true]`/`[exported=false]` when declared and `[exported=true(auto)]` when inferred from filters — `(auto)` is Android's inference, not a declaration. A filtered component with **no** `android:exported` while targeting API 31+ prints `[exported=? invalid: android:exported required for targetSdk>=31]` plus a `warning:` line: Android 12+ refuses to install that manifest, so the app never runs on a modern device. Filters print `action`/`category` lines and one `match: schemes=[…] authorities=[…] paths=[…] mimeTypes=[…]` line: Android pools **every** `<data>` element of a filter per attribute dimension (a scheme in one `<data>` matches a host in another) — when the filter has more than one `<data>` the line says `(pooled across <data> elements: every dimension is matched independently)`. But pooling is not a blank cheque: `scheme` and `host` are looked for across the whole filter, so a declared host without a scheme and a declared path without scheme+host are **inert** — the line then prints `[declared but ignored by Android: … — no android:host is declared, so ports and paths are ignored]` (or the `no android:scheme` variant) instead of presenting them as active restrictions. A MIME type with no scheme adds `(MIME type without a scheme: content: and file: URIs also match)`. API 35 `<uri-relative-filter-group>` children print as `uri-relative-filter-group allow=…: …` lines followed by `warning: <uri-relative-filter-group> (API 35) is reported as declared and NOT evaluated — this filter's URI match surface is incomplete`; that warning means the file needs a hand read, not that the filter is fully modelled. Never read `data …` per element as independent URIs. `meta-data:` lines print `name = value` / `resource=@0x…`. It tolerates the manifest tampering Android itself ignores (zeroed root chunk type, garbage string-pool slots, garbage chunks after `</manifest>`), and non-Android namespaces (`tools:`, `dist:`) never alias android: attributes. Exit `2` = the manifest really is unparseable (or absent).
- `--paranoid`: use when `getclass` shows `long v = -123…L; X.y(v)` pairs (a static `(J)String` call) or `findrefs string` misses text you know exists. `getclass` then shows the decoded literals; `findrefs string` also matches decoded values. Only ids that are a `const-wide` in the same basic block get decoded; other calls stay as-is. The output is rewritten bytecode, not the original. Say so when you quote it.

- `--decode-xor`: use when strings in the sample are hidden as `byte[] a = {8, 7, …}; X.i(a)` (a static `([B)String` decoder that XORs every element with a literal key) — common in packer stubs (verified on a Virbox sample). `findrefs string` also matches decoded values; `getclass` replaces provable calls with the decoded literal (the array-building code stays as dead code). Only sites proven on **every** path are patched: the key must be a literal, all elements constant (`const`+`aput-byte` chains or `fill-array-data`), the bytes valid UTF-8, and no alias of the array read after the call (the decoder mutates in place). Unprovable sites stay as-is — absence of a decode is not evidence of a hidden string. Like `--paranoid`, the output is rewritten bytecode, not the original.

## Workflow

1. Malware/unknown sample: start with `manifest` (permissions + exported components/receivers are your first IOCs), then `listclass <apk>` → file, then filter for candidates (obfuscated APKs: search by package/pattern).
2. `findrefs` with the narrowest predicate (`--class` + name beats name alone). Matching is substring: short names (`get`, `http`) flood results.
3. `getclass` on interesting callers/classes.
4. Redirect big output: `-o out.txt` (findrefs appends; `listclass`, `manifest`, `inspect`, `native` and `cert` overwrite and print nothing to stdout).

## Signing certificates (`cert`)

Lists JAR v1 (`META-INF/*.RSA|DSA|EC`) and APK Signature Scheme v2/v3/v3.1 signers with SHA-256/SHA-1 fingerprints, subject/issuer/serial/validity, algorithm IDs (full `u32`) and the v3 SDK range. **Nothing is verified**: no signature, digest, chain or trust check, so a fingerprint identifies a certificate, not the integrity or authorship of the APK (`verification: not_performed` in text and JSON). Roles: `signer` is the first v2/v3 certificate or the v1 certificate matching the SignerInfo issuer+serial; the rest are `chain`, or `unmatched` if the v1 signer cannot be identified. Scheme equality is stated only when SHA-256 sets match; differences are shown (not an error). Unknown signing-block pair IDs are listed verbatim. `subject == issuer` is shown but never claimed as self-signed. Subjects print in encoded order (openssl `-nameopt RFC2253` prints reversed). `no signing material found` does not mean unsigned/valid. Malformed signing data prints the partial report and exits `2`, as does a raw `.dex` or unreadable input; ZIP64 archives report the signing block as `unsupported` (scheme status `unknown`).

## Resource table (`resources`)

Reads `resources.arsc`: without filters it prints packages, entry/config counts and per-type counts. `--id 0x7f020000` lists every config variant of that ID (ID = package<<24 | (type+typeIdOffset)<<16 | entry index; the key-string index is a different field). `--strings PAT` is a case-sensitive substring over key names (`matched=key`) and string values (`matched=value`, including bag items); `--limit N` (default 100) caps printed hits, `matches:` still shows the total. `TYPE_STRING` values come from the table's global pool; references print as raw `@0x…` IDs (system `0x01…` included, never resolved). A `res/…` value is the path the table claims, not proof the file is a valid resource. Config text is `default` or locale/dpi/vNN plus `raw=<hex>`. No `resources.arsc` entry: text says so, exit `0`. Undecodable string slots read as empty and are noted in `diagnostic:` lines; a malformed chunk is skipped (the walk never guesses the next chunk), the report says `INCOMPLETE` and the exit code is `2`. Raw DEX or an unparseable table exits `2`. Values are display strings and not aapt2-equivalent; compact/sparse/offset16 layouts follow AOSP but are only synthetic-tested (the corpus has dense layouts, package `0x7f`).

## Native libraries (`native`)

Scans `lib/**.so` and `assets/**.so` (in memory, never written to disk; 64 MiB cap each) and every native method (`ACC_NATIVE`) in both direct and virtual lists of all DEX (including DEX-041 members). Methods are joined to libs by JNI symbol name (short and long form). A match is a *candidate* link, not proof. `unbound` = no `Java_*` export of that name: dynamic registration (`RegisterNatives`) is possible but NOT detected or resolved. `abi_dir` is reported next to `e_machine` and can disagree (`MISMATCH`). Symbol table comes from section headers, else `PT_DYNAMIC`; `symbol_source: none` or `[INCOMPLETE]` means exports are unknown, not zero. Split APKs (`config.*.apk`) carry libs but no DEX: pair them with the base APK by hand. Both `--format json` and text list every native method.

## Packed APKs

`asc-rs inspect` automates the checks below. `packer: virbox` needs >= 2 independent Virbox signals (stub class `Lv<hex>/l<hex>;`, `assets/l<hex>_{a32,a64,x86,x64}.so` family, the string "Virbox"). Other packers are NOT identified (no rule verified yet): `packer: none identified` does not mean unpacked. "tail bytes" = bytes past what the DEX map declares; it is only reported when the map gives an exact extent (`coverage unknown` otherwise, and never read as 0) and is an appended-payload *candidate*, not proof. Entropy is from a <=1 MiB prefix and unverified. `--format json` gives the full per-entry inventory; text lists only dex/elf/zip entries.

`inspect` memory: it reads every `classes*.dex` byte (checksum, SHA-1, Virbox string scan) plus up to 1 MiB of each entry for entropy. On STORED APKs those are mmap page touches, so its peak working set grows with DEX size (measured ~83 MiB on a 76.6 MiB APK with 53 MiB of STORED DEX) while private memory stays ~8-10 MiB (`read_bytes = 0`; clean file-backed pages, reclaimable). Other commands touch far less (`cert`/`manifest`/`resources` ~5-15 MiB on the same file). Do not read a large working set as a leak.

Suspect a packer when `listclass` returns only a few classes but `classes.dex` is large (MBs), and manifest components (e.g. `…LoginActivity`) are missing from `listclass`. The real DEX is encrypted and appended to or hidden beside a stub; no static tool (asc-rs or jadx) can see it.
- Virbox signs: stub classes `Lv<hex>/l<hex>;` (+ `$inner`), the string `"Virbox"` (`findrefs string Virbox`), native methods `I<hex>_00…05`, `assets/l<hex>_{a32,a64,x86,x64}.so`.
- Report only the stub + manifest as analysed; say the payload was not. Next step: runtime dump (BlackDex / frida-dexdump), then run asc-rs on the dumped DEX (zip it as `classes.dex` in an APK).

## asc-rs vs jadx class counts

`listclass` lists only classes defined in `classes*.dex` (what ART loads). jadx also shows nodes for components declared in the manifest (even when no DEX defines them) and for embedded Java class files (e.g. `DebugProbesKt.bin`, magic `CAFEBABE` → `kotlin.coroutines.jvm.internal`). jadx showing more is expected, not an asc-rs bug. Use `manifest` to see declared-but-absent components.

## Pitfalls

- On Windows, piping to `head` prints a harmless "pipe has been ended" panic; use `-o` and read the file.
- On Windows, paths with non-ASCII characters (e.g. Vietnamese file names) can make captured stdout come back empty. Use `-o FILE` and read the file (set `PYTHONIOENCODING=utf-8` if a Python helper prints).
- Constructors/static init are `<init>` / `<clinit>`.
- Multidex is automatic (`classes*.dex` numeric order); `dex_name` says which.
- A process-wide 2 GiB budget caps DEX bytes held by concurrent `getclass`/`disasm`/`findrefs` scans. An APK large enough to hit it fails with `memory budget exceeded` (exit `2`; `findrefs` records it per DEX and still exits `2` with partial output) — that means the input is pathological for this machine, not that the tool is broken.
- Smali, CFG, and call-graph output: `disasm` DOES produce Smali-syntax listings (whole class or `--method`), and `findrefs`/`getclass` cover references and one class. But there is no CFG or call-graph output. Don't fabricate those; say the tool can't provide them.
- **Deep links / intent filters: never treat each `<data>` element as an independent URI.** Android pools every `<data>` of one `<intent-filter>` per attribute dimension, so a scheme in one element matches a host in another — `manifest` prints one pooled `match:` line per filter for exactly this reason. A filter reading `scheme=https host=a.example.com` + `scheme=myapp host=b.example.com` also matches `https://b.example.com` and `myapp://a.example.com`. The dimensions are **dependent** though: with no `scheme` anywhere, hosts, ports and paths are ignored outright; with a scheme but no `host`, ports and paths are ignored (`IntentFilter.matchData` nests the authority loop inside `schemes != null` and the path loop inside the authority branch). Such inert attributes are still printed, labelled `[declared but ignored by Android: …]` — do not report them as reachable URLs. A `mimeType` with no scheme instead matches intents carrying no URI plus `content:`/`file:` URIs (not `http`/`https`). API 35 `<uri-relative-filter-group>` (ANDed, allow/deny-ordered, evaluated after sibling `<data>`) is reported **raw and unevaluated**, with a `warning:` line: for those filters the printed match set is incomplete, so read the manifest entry by hand before concluding which deep links are reachable.
- A component with an intent filter and no `android:exported` while the app targets API 31+ is an **invalid manifest**: Android 12+ refuses to install it. `manifest` prints `[exported=? invalid: …]` and a `warning:` line — do not report such a component as a working exported entry, and do not silently "fix" it to `exported=false`.
- Smoke-test on any small APK you have; verify the binary runs with `asc-rs --help` before relying on it.
